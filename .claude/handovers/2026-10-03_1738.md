## strands-decider の仕様（比較に関わる点）
- API: `POST /v1/systemone`。state、名前付きの質問、Noul と criteria の形は Jev と同じ。応答は `answers.<名前>.noul`、`usage`、`latency_ms`。「Jev との互換性は確認していない」と明記
- モデル v19（`StrandsAgents/strands-decider-2B-hobson-v19`）: Qwen3.5-2B-Base に LoRA と読み出し部を付けた 1.9B。モデル本体と重みは HF キャッシュに取得済み
- 入力の上限: `max_length` 4096（v19 の設定）。質問が先に枠を取り、state は残りに収まるよう切り詰められる。0.1.0 では警告もエラーもなく切り詰める（ドキュメントの `--strict-window` は 0.1.0 にない）
- state は `json.dumps(indent=2, ensure_ascii=False)` でそのまま入る。`candidates[0].text` のような経路を解釈する仕組みはなく、学習データにもその書き方は見当たらない
- 複数の質問は state を 1 回だけ読み、独立に評価する（1 回の処理で最大 32 問）
- 同時リクエストは検証されていない。内部の競合（issue #9）があるので、1 件ずつ順に送る必要がある
- 言語: 日本語を含む他言語への対応の記述はない。学習データは英語の分類データが中心。検索の関連度判定のデータは含まれない
- JevBench 公開課題の正答率 0.723（89 システム中 50 位、2B クラス 3 位）
- 手元の環境: RTX 3060 Ti（8GB）、torch 2.14.1+cu130 で CUDA 利用可。flash-linear-attention と causal-conv1d は未導入なので遅い代替の処理で動く。WSL に `nvidia-smi` はない

## 決定事項
- 「同一条件」はデータ、指示文と判定基準（Jev と同じ日本語）、指標の計算（report-judge）でそろえる
- 送る前に strands-decider のトークナイザーで state のトークン数を数え、上限を超える組は送らずに記録する（黙って切り詰められた結果を混ぜないため）
- リクエストは 1 件ずつ順に送り、1 問あたりの時間と `latency_ms` を記録する。Jev（ネットワーク越し、8 並列）とは条件が違うことを明記する

## 捨てた選択肢と理由
- Jev の測定（8 並列）と同じ並列度で送る案: strands-decider は同時リクエストが未検証で内部に競合がある — 1 件ずつ順に送る
- 候補文書 10 件をそのまま 1 つの state に入れる案: 日本語 10 件は Jev の請求トークンで約 4,800 で上限 4,096 を超える見込み、かつ経路の指定を解釈する仕組みがない — 1 件ずつと、上限に収まる件数でまとめる形の 2 通りを測る案を提示した

## ハマりどころ
- `git filter-repo` と強制 push は Claude Code の自動モードの安全判定で拒否された → ユーザーの許可で filter-repo は実行できたが、強制 push は再度拒否 → ユーザーが `!` で実行した
- zsh では `echo =====` が「==== not found」になる（`=word` の展開）。区切りには別の文字を使う
- zsh で `grep --include=*.py` がグロブ展開で失敗する → 引数を引用符で囲む

## 学び
- strands-decider 0.1.0 のサーバーは `127.0.0.1` に認証なしで立つ。`latency_ms` を応答に含む
- JevBench の `typesafe` アダプタは strands-decider のサーバーに無変更で通る（公式の記述）。今の Jev クライアントも接続先を `http://127.0.0.1:<port>/v1` に向ければ使える見込み（未検証）
