# 引き継ぎノート 2026-09-20

Claude デスクトップアプリでの作業を Claude Code へ移すための引き継ぎ。

## いまどこにいるか

やりたいことは「Jev を使うと従来のRAGより検索精度が上がるのか」を、公式ユースケースごとに横並びで測り、最終的にブログ記事にすること。

この日、素材を白書PDFから JQaRA（日本語の検索評価データセット）に入れ替え、リポジトリを組み替えた。PDF処理と自作の正解ラベルは全部捨てた。検証済みだった Jev クライアント実装（`src/jev_rag/jev/`）はそのまま残してある。

残っている作業は実測1回とその結果の整理だけ。コードは動く状態で、認証情報を入れれば `jev-rag evaluate` が数字を出す。

## 次にやること

1. `.env` に鍵を入れる。`AI_GATEWAY_API_KEY`（Jev用）と AWS の認証情報（Bedrock用）。
2. `uv run jev-rag check` で Jev の疎通を確認する。
3. `uv run jev-rag prepare` で JQaRA を取得する（60MB、`data/raw/` は追跡対象外）。
4. 小さく試す。`uv run jev-rag evaluate --queries 10 --candidates 30`。ここで各経路が動くこと、費用感、所要時間を掴む。
5. 本番。`uv run jev-rag evaluate --queries 300 --candidates 30`。結果は `out/results.json` に残る。
6. `uv run jev-rag report --movers jev_crossencode` で、従来手法が沈めた正解をJevが引き上げた具体例を出す。記事にはこれが効く。
7. `uv run jev-rag context` で文脈選択の効果（削減量と正解の保持率）を測る。
8. 記事にまとめる。README がそのまま骨子になる。

## 判断が要りそうな分岐

問題数。100問でも傾向は出るが、経路間の差が小さい場合に偶然と区別しづらい。300問あれば十分。費用は全経路でも数十円の範囲。

候補数。30件が既定。JQaRA本来の100件で回すと公開スコアと厳密に比較できるが、クロスエンコードのリクエストが3.3倍になる。まず30で傾向を見て、結論が出そうなら100で確定させるのがよい。

指示文のチューニング。いまの `src/jev_rag/jev/prompts.py` は日本語で書いた初期値で、一度も調整していない。従来手法は既製サービスをそのまま呼んでいるので条件が対等でない。Jev側だけ磨くと不公平になるが、逆に初期値のままだとJevを不当に低く見せる可能性もある。記事ではどちらの立場を取るか決めて明示したほうがよい。

S3 Vectors。当初の前提に入っていたが、JQaRA は候補が最初から与えられる課題なので、比較にベクトルストアは要らない。無理に挟むと複雑さだけが増える。実運用に近い経路を別途見せたいなら追加する余地はあるが、比較の本筋からは外してある。

## 触ってはいけない前提

候補のシャッフル（`dataset.py`）。候補を絞るとき正解を優先して残すので、シャッフルしないと入力順に正解が偏り、何もしない経路でも満点が出る。実装当初これが起きて nDCG が 1.000 になった。テストで固定してある。

state の参照記法（`src/jev_rag/jev/state.py`）。質問の instructions から候補を指すときは、バックティック付きのドット・インデックス記法を state ルートからの相対パスで書く（例: `` `candidates[3].text` ``）。`state.` 接頭辞は付けない。質問IDはモデルに送られないので、どの候補についての判定かを伝えられるのは instructions だけ。候補は配列で渡し、位置で参照する。質問キー（doc_id）とパス（位置）が別物になるため、両者がズレると全候補が静かに誤採点され「日本語が苦手」に見える。`tests/test_state_paths.py` がこの対応を固定しており、AST を歩いて古い書き方の再発も検出する。Choice の選択肢キーはモデルに見えるので、doc_id ではなく中立なラベル（a / b）を使い、説明文でパスを示す。

パッセージの作り方（`dataset.py` の `passage_text`）。JQaRA 公式の評価スクリプトは既定で `f"{title} {text}"` を連結してからモデルに渡す。README が並べている公開スコアはその形で出た数字なので、本文だけを採点すると同じ土俵に乗らない。

`.claude/docs/research/typesafe/` は公式ドキュメントの逐語コピー。実装の照合基準なので整形しない。ruff の対象外にしてある（`pyproject.toml` の `extend-exclude`）。

`src/jev_rag/usecases.py` は公式ユースケースと実装の対応をコードに固定したもの。モジュール名や経路名を変えると `tests/test_usecases_registry.py` が落ちる。落ちたら表のほうも直す。

## 検証済みのこと、未検証のこと

検証済み。Jev のリクエスト/レスポンス形式、3プリミティブの `criteria` の型、Choice最大255件、Score 2〜10段階、トークン予算（64k / 32k）、AI Gateway の model id と base URL。いずれも公式ドキュメントと突き合わせた。S3 Vectors の呼び出しも botocore のサービス定義と照合した（ただし現構成では使わない）。

未検証。Jev への実リクエストは一度も送っていない。Bedrock の呼び出しも実行していない。つまり「Jevで改善したか」という数字はまだ1つも出ていない。ここが次の作業の全て。

## 過去の経緯（読まなくてもよい）

最初は総務省『情報通信白書』のPDFを素材にしていた。PDF抽出には装飾用の字間、二重描画、全ページの柱といったアーティファクトがあり、その正規化に相当のコードを費やした。また正解ラベルを自作する必要があり、キーワードルールと句点密度による較正まで作った。どちらも検証の本筋ではないので破棄した。記録は `.claude/docs/archive/` に残してある。

外部サイトへのアクセスが長くポリシーで遮断されており、公式ドキュメントを二次資料から推測して実装していた時期がある。開通後に全部照合し、誤っていた箇所（「1リクエスト32問」という存在しない上限など）は直した。
