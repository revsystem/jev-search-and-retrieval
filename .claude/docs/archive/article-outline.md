## 記事の結論

検索は埋め込みで候補を絞り、絞った候補の関連度の判定を Jev に任せると、従来の rerank（Cohere Rerank）より関連する文書を正確に上位へ集められる。Jev だけで検索全体を置き換えることは、数千件を超える規模では所要時間の点で現実的でなく、精度も確かめていない。

## 1. 導入

「Jev as a Judge」は論文 "JEV-as-a-Judge: Accept When Confident, Escalate When Unsure"（Li ほか、2026-09-22、https://arxiv.org/abs/2609.26550 ）の言葉である。論文が扱うのは生成された回答の評価（回答の優劣、根拠に照らした事実性、参照解答との照合）で、検索・rerank・関連度判定は扱っていない。論文の要点を短く紹介する。

- 最上位の LLM 判定器に3ポイント以内の精度を、0.36%の費用で出す
- 推論・導出の正しさの確認や、誤った回答のほうが丁寧に書かれている場合には大きく劣る
- 確信度が高いものだけ受け入れ、低いものを強い判定器に回す二段構えを提案している
- 判定1件の中央値は0.152秒

そのうえで問いを立てる。型の保証と速さに加えて判定の質も実用水準にあるなら、その判定器としての性質を検索結果の関連度判定に持ち込んだらどうなるか。RAG の rerank に入れると、関連する文書をより正確に上位へ集められるのか。論文の主張を超えないよう、ここから先は論文ではなく今回の測定で答える、と明示する。結論もここで先に示す。

注意: 論文の数値は取得ツールの要約経由で確認しただけなので、書く前に原文で照合する。

生成された回答の質は「関連する文書を上位に集められるか」とは別の観点なので、この記事では扱わないと断っておく。

## 2. Jev の基本的な仕組み

概要。state（判定の材料）と、名前付きの質問を送る。質問は state に対して並列に評価され、互いの答えは見えない。Noul は確率、Choice は選択肢、Score は数値を返す。

- Jev のモデル
- 32k と 64k の制約（state と一番長い質問で32k、state と全質問で64k）
- state の例と、そこに入れる材料と質問3つの具体例

```
state（候補3件）を1回読む
   ├─ 質問d1 を state に対して評価 → 0.97
   ├─ 質問d2 を state に対して評価 → 0.31   ← d1の答えは見えない
   └─ 質問d3 を state に対して評価 → 0.02   ← d1もd2も見えない
```

- トークンの数え方の例
- 候補を10件ずつに分けると state が32kに収まる話（100件でも約2万トークンで収まるが、収まることと精度が保てることは別で、それは6章で示す）

## 3. 比べ方

rerank の良し悪しを、判定器としての精度で測る。質問と文書の組ごとに「関連／無関係」を当てられるかを見る。

- 比べる経路: BM25、埋め込み（Cohere Embed v4）、Cohere Rerank、Jev（10件ずつ／1件ずつ）
- 主な指標: PR-AUC（全組をまとめた判定の正確さ）。補助に問題内ROC-AUC（1つの質問の候補を正しく並べられるか）、ECE（確率の当たり具合、Jev のみ）
- 差には問題単位の bootstrap 95%区間を付け、区間が0をまたがないものだけを差として扱う

指標は専門用語を避けて1つずつ言い換える。読者は ML の専門家でない想定。

## 4. データ

3つを使い、混ぜずに別々に集計する。

- MIRACL 日本語: 実際の検索結果に人が関連の有無を付けたデータ。ラベルが観測に基づくので、結論の土台にする。質問は一問一答型
- J-RAGBench: 架空企業の業務寄りの問い。語の一致（BM25）だけでかなり解ける点を注記する
- 合成データ60問: 比較・理由・経緯・複数要因・統合といった、一問一答で終わらない業務の問い

合成データの作り方は丁寧に書く。正解は作り方で決め、別の LLM に後から判定させない理由。負例は同じ会社・同じ語・同じ話題で、必要な事実だけがない。素朴な判定器（長さ、語の一致、BM25）が偶然水準であることを関門にしたこと。途中で手がかりの漏れが見つかって作り直した経緯（観点の列挙、正例だけ長い、負例の自己否定文）も短く触れる。生成と検証を別のモデルが担い、検証は設計図を見ずに行い、食い違い0件、1割を目視確認。

## 5. 結果1: 判定の正確さ

3データの横並びの表（BM25 / Cohere / Jev と差の区間）。

- どのデータでも Jev が Cohere を上回った
- MIRACL で +0.069。これが一般的な検索での目安
- 合成データでは +0.56。Cohere は BM25 と区別できない水準まで落ちた。話題の近さに頼る判定器は、同じ話題で中身の違う文書（版違い・年度違い・部署違い）を見分けられない。ただしこの幅は作り方に依存し、上限寄りの値として扱う
- なぜ差が出るのかを、仕組みの違いとして説明する。Cohere Rerank（rerank-v3-5）は関連度を出すよう訓練されたモデルで、何を「関連」とみなすかはモデルに組み込まれており利用者は変えられない。Jev は、こちらが言葉で書いた判定基準（「クエリが指す対象そのものを扱い、回答を裏づける事実・数値・定義を含む」なら真、「話題が重なるだけ、参照先が異なる、根拠となる情報を含まない」なら偽）に当てはまるかの確率を返す。合成データで Cohere が BM25 と同じ水準まで落ちたことは、Cohere の「関連」が話題の近さに寄っていることを示す
- 差がモデルの力か判定基準の力かを、基準を渡さない版（「関連しますか」とだけ問う）で切り分けた結果を示す。基準なしでも3データすべてで Cohere を上回り（合成 +0.53、J-RAGBench +0.08、MIRACL +0.035、いずれも区間は0をまたがない）、合成データの差のほとんどはモデル自体の判定から来る。基準が足すのは PR-AUC で +0.01〜0.03 にとどまる
- 基準の効果は確率の当たり具合に大きく出る。基準なしの Jev は「関連」に大きく寄り（MIRACL で0.5で切ると適合率0.40・再現率0.98）、基準を書くと ECE が半分前後に下がる。並べ替えの質はモデルで決まり、閾値で切る判定器として使うなら関連の定義を書くことが効く、とまとめる
- Jev の弱点も書く: MIRACL では確率の当たり具合が悪く、0.5で切ると関連寄りに判定する（再現率0.89、適合率0.60）。論文の「誤った回答が丁寧に書かれていると騙されやすい」と似た現象の可能性に触れてよいが、確かめていない推測として書く
- 所要時間は参考として載せる（MIRACL 8,354組で Jev 285秒、Cohere 389秒）。並列8で送った今回の実装での値で、速度の優劣を一般化はしない

## 6. 結果2: 1回に何件載せるか

- 同じ質問の候補10件をまとめて判定させると、1件ずつより正確（+0.158）。並べて比べられるため。Cohere は1件ずつ独立に採点するので、この比較はできない（5章の仕組みの違いとつなげる）
- 同じ10件ずつでも、中身が無関係な文書なら1件ずつと変わらない。効いているのは件数ではなく、一緒に載る中身
- 無関係な文書が25件までは影響がなく、50件を超えると崩れる。100件では無関係な文書の半分近くを関連と判定する
- したがって「検索で絞った同じ話題の候補を10件ずつ渡す」が一番よく働く形

## 7. retrieve の線引き

Jev だけで検索する場合の所要時間の見積もり表（1,000件で十数秒〜30秒、1万件で数分、100万件で数時間）。

- 見積もりの根拠と仮定（並列8、件数に比例）
- 精度は測っていないこと、測らなかった理由（全件にラベルの付いたデータがない。ラベルのない文書を無関連と見なすと、Jev が本当に関連する文書を拾ったときに誤りと数えてしまう）

## 8. まとめ

構成の推奨: 埋め込み検索で候補を絞る → 絞った候補を10件ずつ Jev で判定して並べ替える。

## 9. 言えること、言えないこと

- 日本語データだけで測った
- 合成データの正解は作り方で定めたもので、観測ではない。主張は MIRACL と向きが一致した部分に限る
- J-RAGBench と合成データは60問ずつで、区間が広い
- Jev は direct 経路のみで測った
- 判定基準は「あり」（1種類）と「なし」の2通りしか試していない。別の書き方でどこまで変わるかは測っていない
- Jev だけの検索の精度は未検証
