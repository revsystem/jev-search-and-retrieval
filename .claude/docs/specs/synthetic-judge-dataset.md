# 判定器評価用の合成データセット仕様

## 目的

検索結果の関連度を判定する「判定器」として、Cohere Rerank と TypeSafe Jev の精度を比べる。クエリと文書のペアごとに関連/無関連を当てられるかを、PR-AUC・ROC-AUC・較正（ECE）で測る。

公開データ（J-RAGBench、MIRACL 日本語）には、一般的な業務RAGの問い（比較・理由・経緯・複数要因・複数文書の統合）がほとんど含まれない。このデータセットはその不足を補う。公開データは手を加えずに別途使い、このデータとは混ぜずに集計する。

## 最重要の原則

正解ラベルは作り方で決める。LLM に後から「この文書は関連か」を判定させて決めてはいけない。判定器の精度を測るデータの正解を別の LLM が決めると、測っているものが「その LLM との一致率」になるためである。

具体的には、質問に答えるのに必要な事実（required_facts）を先に決め、それを載せた文書を正例として書き、載せない文書を負例として書く。どの文書が関連かは、生成時の設計図に記録される。

## 形式

1問につき1ファイル、JSON。ファイル名は `<id>.json`。

```json
{
  "id": "a-001",
  "domain": "人事・総務",
  "question_type": "comparison",
  "question": "…",
  "required_facts": [
    {"id": "f1", "fact": "…"},
    {"id": "f2", "fact": "…"}
  ],
  "documents": [
    {"doc_id": "a-001-d01", "role": "positive", "contains_facts": ["f1"], "text": "…"},
    {"doc_id": "a-001-d02", "role": "negative", "contains_facts": [], "near_miss": "同じ会社の別の年度", "text": "…"}
  ],
  "reference_answer": "…"
}
```

`role` が `positive` の文書は `contains_facts` が1件以上、`negative` の文書は空。これが正解ラベルになる。

正例の定義に注意する。required_facts を1件でも含む文書は正例である。その文書だけでは質問に答えきれなくても、検索で拾うべき根拠だからである。判定器の評価で問うのは「この文書は根拠として拾う価値があるか」であって、「この文書だけで答えられるか」ではない。

## 作り方の規則

架空の企業・製品・人物・地名だけを使う。実在のものは使わない。モデルが世界知識で答えられないようにするためと、権利上の問題を避けるため。

質問は一問一答にしない。`question_type` は次の5種で、ほぼ均等に作る。

- comparison: 2つ以上の対象の比較（部署間、期間、製品、制度）
- reason: ある結果の理由・原因
- process: 経緯・手順・変遷
- multi_factor: 複数の要因や条件の組み合わせで決まる判断
- integration: 複数の文書の情報を統合しないと答えられない問い

答えるのに正例が2件以上必要な形にする。required_facts は2〜4件で、それぞれ別の文書に載せる（1文書に全部載せない）。

1問あたり文書は10件。正例は2〜4件、残りは負例。

負例は紛らわしく作る。質問に出てくる固有名詞や用語を含み、同じ話題を扱い、しかし required_facts をどれも含まず、質問のどの部分にも答えない。near_miss に紛らわしさの種類を書く。例:

- 同じ会社の別の年度・別の期
- 同じ指標の別の会社・別の部署
- 同じ制度の改定前の版
- 具体的な数値や条件のない一般論
- 同じ用語を別の意味で使っている文書
- 質問の前提の一部だけに触れ、肝心の部分がない文書

キーワードの一致だけで見分けられてはいけない。負例にも質問の語を正例と同程度に含める。

正例と負例で文体と長さを揃える。1文書あたり150〜400字。社内規程、決算説明資料、議事録、プレスリリース、FAQ、仕様書、社内報など、業務文書の断片として自然な書き方にする。

文書の本文に手がかりを入れない。「本件とは関係ないが」「参考までに」のような、関連性を示唆する言い回しを使わない。文書の順序で正例がまとまらないよう、documents の並びは正例と負例を混ぜる。

reference_answer は、required_facts だけから導ける模範解答を100〜300字で書く。

## 生成の進め方

既に存在するファイルは作り直さない。1問書くごとに保存する。途中で止まっても、次に起動したときに続きから再開できるようにするため。

担当ディレクトリの外には書かない。Jev や Cohere を呼ばない。評価の実行もしない。

## 検証の進め方

検証は仕様への適合の確認に限る。検証担当に「この文書は質問に関連するか」を判断させてはいけない。それは判定器が評価される作業そのものであり、生成側と検証側が同じ盲点を持っていれば、検証しても区別できないからである。

確認するのは、確かめられる性質だけである。

1. 各文書に、各 required_fact が述べられているか（`facts_stated`）。事実の中の具体的な数値・条件・固有名詞が本文に書かれているかで判断する。話題が近いかどうかではない。
2. 各文書に、関連性を示唆する言い回し（「本件とは関係ないが」「参考までに」など）がないか（`leak_phrase`）。
3. 質問全体について、required_facts を1つの文書だけで全部満たせてしまわないか（`needs_multiple_docs`）。一問一答（「〜はいつ」「〜は誰」「〜は何円」）になっていないか（`non_factoid`）。required_facts だけから答えが導けるか（`answerable_from_facts`）。

検証担当は設計図（role、contains_facts、near_miss）を見ない。司令塔が、それらを取り除き文書の順序を入れ替えた「検証用ビュー」を `data/synthetic/views_a/`、`data/synthetic/views_b/` に用意する。検証担当はそれを読む。

検証結果は1問につき1ファイル、`<id>.json`。既存のファイルは作り直さない。

```json
{
  "id": "a-001",
  "verdicts": [
    {"doc_id": "a-001-d01", "facts_stated": ["f1"], "leak_phrase": false, "note": ""}
  ],
  "question_checks": {
    "needs_multiple_docs": true,
    "non_factoid": true,
    "answerable_from_facts": true,
    "note": ""
  }
}
```

司令塔は設計図と検証結果を突き合わせる。`facts_stated` が `contains_facts` と食い違った文書、`leak_phrase` が真の文書、`question_checks` のいずれかが偽の問題を一覧にする。食い違いはユーザーが確認するか、その問題を捨てる。最後に全体から1割をランダムに抜き、ユーザーが目視で確認する。

## 健全性の検査

司令塔が次を数値で確かめる。これは Jev と Cohere の測定（有料）の前に通す関門である。ここで落ちたら、その上で何を測っても意味がない。

- 質問との語の重なりが、正例と負例で揃っているか
- 文書の長さが、正例と負例で揃っているか
- 長さだけ、語の一致だけ、BM25 で判定する素朴な判定器の PR-AUC。これが高いなら、作り方に手がかりが漏れている

## このデータで言えること、言えないこと

このデータの正解は、作り方で定めたものであって観測したものではない。したがって、Jev と Cohere のどちらが「作り方で定めた関連」によく一致するかは示せるが、どちらが現実の関連をよく判定するかを単独で決めることはできない。

MIRACL 日本語はその裏付けになる。ラベルは実際の検索候補を人が判定したもので、由来が観測に基づく。質問の型を合成データが、ラベルの由来を MIRACL が補う。結論として主張できるのは、両方で同じ傾向が出た部分だけである。

## 分担

| 担当 | ディレクトリ | 領域 | id |
|---|---|---|---|
| 生成A（claude） | `data/synthetic/gen_a/` | 人事・総務、経理・財務、法務・コンプライアンス | a-001〜a-030 |
| 生成B（cursor） | `data/synthetic/gen_b/` | 製造・品質管理、IT・情報システム、営業・マーケティング | b-001〜b-030 |
| 生成Aの検証（cursor） | `data/synthetic/verify_a/` | | |
| 生成Bの検証（claude） | `data/synthetic/verify_b/` | | |

各領域10問、5種の question_type を各2問。
